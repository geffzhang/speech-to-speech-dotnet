## 协议层差分语料（同上，第二轮）

### 关键发现：基线不用起服务就能录

上游 `RealtimeService` 的 handler 全是 **`(conn_id, event) -> list[ServerEvent]`** 的纯函数，
`RealtimeService(text_prompt_queue=Queue(), should_listen=Event())` 直接可实例化，
**不需要模型、不需要 FastAPI、不需要网络**。`svc.response._build_response(cid, status)` 也能直接调。

代价是装依赖：`openai==2.28.0`（与上游 pyproject 锁定一致）+ `numpy` + `scipy` + `starlette`。
`scipy` 那次 pip 报 502 但 import 却通过了——说明它只在某条可选路径上，别被这报错误导。

### 两个真实缺陷（重点）

**1. JSON 序列化把中文和 base64 特殊字符转义了（C012，已修）**

本实现原先 `new JsonSerializerOptions { WriteIndented = false }` —— 默认 `JavaScriptEncoder`。
实测 `"你好，世界 +/="` 上线成了 `"\u4F60\u597D\uFF0C\u4E16\u754C \u002B/="`：
汉字 3 字节变 6 字节（**中文载荷体积翻倍**），base64 里的 `+` 变 `\u002B`。

上游 `transports.py` 走 Starlette 的 `ws.send_json`，其源码是
`json.dumps(data, separators=(",", ":"), ensure_ascii=False)` —— **不转义**。

修法：`Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping`。
顺带把探针改成调用 `ServerEvent.Serialize`，否则探针自己 `ToJsonString()` 就测不到产品路径。

（`websocket_router.py:709` 另有一处 `model_dump_json()`，pydantic 默认也不转义，两条路径一致。）

**2. 服务端事件只覆盖 16/26（D013）**

`tools/refprobe/protocol_coverage.py` 反射上游 `ServerEvent` 联合类型，与本实现 `EventNames` 对比：
覆盖 61%。缺的 9 类里最要命的是 `response.output_item.added` / `response.content_part.added` ——
**OpenAI 官方客户端靠这两类建立消息项与内容片，缺了整段回复可能渲染不出来**。

其余缺口：`transcription.completed` 缺 `usage`（官方 schema **必填**，D011）；
`response` 对象缺 `usage`/`output_modalities`/`conversation_id`（D012）；
`conversation.item.created` 的 item 缺 `content` 数组与 `previous_item_id`（D014）。

## 回合续（13:00–14:00）收尾三件事：终态语义、C015、D011

### `status_details.type` 必须与 `status` 同域（C015）

原先工厂里 `status_details.type` 是硬编码 `"incomplete"`，取消时就产出
`{type: incomplete, reason: client_cancelled}` —— 官方 schema 里不存在这个组合，
按判别器解析的客户端会拒收或误判。改为 `type = status`：
`completed` 不发 `status_details`；`cancelled`/`incomplete`/`failed` 各发同名 type，
`failed` 额外带 `error.code`/`error.message`。

### 协议语料补到 32 条

- 终态三条：`response-done-cancelled` / `-incomplete` / `-failed`
- `transcription-completed`（D011 修复后才可入语料）

新坑：`response.done` 的上游入参是**完整 response 对象**（`{"response": {...}}`），

`conversation.item.input_audio_transcription.completed` 的 `usage` 在官方 schema 里

## 回合续：C006 投机轮次状态机移植 + 新语料层

### 先说结论

上游 488 行 `SpeculativeTurnTracker` 已逐方法移植并**首次运行即 13/13 逐值一致**。
这层新增了一个此前没有的能力：**比状态迁移，不比字节**。

### 为什么这层能差分

三个前提缺一不可，也是以后移植其他状态机的检查清单：

1. **自包含** —— 不碰模型/网络/磁盘，输入是方法调用、输出是返回值
2. **时钟可注入** —— 所有期限都是 `time.monotonic()` 上的绝对时刻。Python 侧把模块里的
   `time` 整个替换成假时钟（`st.time = clock`），C# 侧构造传 `Func<double>`。
   **不注入就无法确定性比对**：真实时钟两侧数字必然不同。
3. **返回值是纯量** —— 裁决枚举 + 轮次 + 期限，比得动

### 两条归一化约定（关键）

- **枚举输出线上值**：`soft_ended` 而不是 `SoftEnded`
- **浮点输出 6 位小数的字符串**：期限是 `起点 + delta/1000.0` 的浮点累加，
  两侧十进制最短表示不同（Python 写 `1000.0`，C# 写 `1000`）。统一成 `"1000.400000"`
  后退化为字符串比较。**不要用容差——有容差就等于允许漂移**。

### 13 条语料守什么

reopen-window / hold-not-drop / committed-never-held / close-keeps-answered /
revision-supersede / pending-hold-expires / grace-only-extends / segment-discarded /
reset-zeroes / configure-reopen-zero / confirm-stale-candidate /
processing-deadline-scope / legacy-no-turn-label

三条不变量是重点：**挂起不等于丢弃**（HOLD 带期限、到期自动 ACCEPT）、
**已提交的不可挂起**、**复开不推进序号**（同一轮 revision+1）。

### 压不住的两块

- **阻塞等待**（`WaitForGate`）：探针会真睡在期限上，比对变成比谁更慢。
  改由 `WaitForGateTests` 7 例锁「等待者怎么被叫醒」。
- **并发**：`threading.Condition` 与 `Monitor` 语义等价但调度不可复现，不靠测试撞运气。

### 接合点（状态机对了 ≠ 用得对）

`VadHandler` 三处、`RealtimeConnection` 两处：

- 开口：**先 `SpeechCandidateStarted` 再 `SpeechStarted`**。反了就少了「压住」那段，
  用户换气时的输出会抢在判定之前发出去。
- 定稿：`SegmentFinalized(endMs, outputHoldMs: speculativeReopenMs)`
- 空段：`SegmentDiscarded()`（放不出去的段要退回 SOFT_ENDED，否则下一句被并进同一轮）
- 响应收口 + 取消两条路径都 `Close`（取消走的是上游同一个 `finish_response`）。
  不释放提交态，这一轮永远停在 ANSWERING、又不能复开。
- 复开窗口 = `max(speculative_reopen_ms, unanswered_reopen_ms)`，**取 max 不取后者覆盖**：
  宽限比上限长时窗口要跟着变宽，否则宽限还没过就判成不能复开。

Smart Turn 判定器未移植 → 恒走「说完了」分支：宽限 800ms、处理延迟 0。

## 回合续：D012 response 载荷 + C016 两处形状缺陷

### 先说发现

做 D012 时对照上游 `_build_response` 读出一处此前判错的行为：
**`status_details` 对任何终态都发，`completed` 也发**（`if reason or status in
("completed","cancelled","incomplete","failed")` —— 这个条件恒真）。
上一轮修 C015 时我按「completed 不发」写的，等于把「正常结束」这条也漏了。
`failed` 的 `error` 也只带 `type`（恒 `response_failed`），本实现多发 `code`/`message`。
两处一并修，登记 C016。

教训：**「异常才发某字段」是直觉，不是上游口径**。补异常分支时容易只想着异常。

### 结构

`ResponseSnapshot`（record）+ `ServerEvent.BuildResponse` 成为 response 对象唯一产地，
`response.created` 与 `response.done` 共用。先前两处各写一份 `JsonObject`，必然漂。
`AssistantMessageItem` 也被 `output_item.done` 与终态 `output[]` 共用——
客户端把这两份当同一条消息的快照，不一致时后到的 done 会把先渲染的盖掉。

### usage 记账

抽成 `ResponseUsageLedger`（可单测），规则照上游 `_on_token_usage`：
- 只有 `responseKey == 当前响应` 才直接累加
- 其余按 key 挂起，收口时 `ApplyPending` 结转
- 已关闭 key 上迟到的用量**丢弃**
- 开新响应只归零计数、**不清**「已关闭」记忆（清了等于拆防护）
- 挂起表与关闭表各 128 上限

两个坑：
1. **HashSet 的枚举顺序不是插入序**。第一版用 `Remove(_closed.First())` 做 FIFO 淘汰，
   实际是随机删——近期 key 可能被先删掉，迟到用量又落进下一轮。改成 `HashSet + Queue`。
2. `_pending` 表不设上限就是慢性泄漏：被打断的投机轮次永远不会被结转。同样加 FIFO 上限。

## 回合续：D017 逐响应音色覆盖打通到合成器

### 补的是什么

`response.create` 里的 `audio.output.voice` 原先被整个忽略：只读 instructions /
temperature / max_output_tokens / output_modalities，音色只认会话配置。

上游是「响应级优先、会话级兜底」，而且**两处都要生效**：
`_build_response` 用它填载荷，`_apply_session_voice_override` 用它改合成器。

### 关键教训：这类缺陷只能靠单测锁，不能靠语料

语料比的是线上字节。把载荷改对、合成器没改，语料照样全绿——
字段对、声音错，只能靠耳朵发现。所以：

- 音色解析收敛成**一个静态表达式**
  `RealtimeResponseCreateParams.ResolveVoice(response, config)`
  协议层与 `TtsInput.Create` 都调它，不许各写一份。
- 锁定用例断言的是**值有没有真的到后端**：`RecordingTts` 记录 `TtsRequest.Speaker`，
  5 例里有 1 例直接断言后端收到的 speaker 是覆盖值，而不只是 `TtsInput.Voice`。
- 空串按「未指定」处理（上游把空音色当作没给），不拿空串去盖会话配置。
- `voice` 两种形态都认：内置名字符串，以及 `{"id": "..."}` 的自定义音色对象。

链路：`response.create` → `ReadVoice` → `ResolveVoice` → `_responseVoice`（载荷）
+ `chunk.Response` → `TtsInput.Voice` → `TtsRequest.Speaker`（合成）。

前几层是「同一份代码的两种语言写法」，这层是**同一个算法的两种实现互证**：
上游 `lingua-py`，本实现 `lingua-rs` 的 .NET 封装。同模型、同算法、不同宿主机语言。
这就是为什么两侧一致才有意义——不一致意味着绑定本身有分歧，必须记进差异账而不是调参对齐。

实测 **15/15 逐值一致**，含置信度差边界、`nb`→`no`、256 码点窗口截断。

### 结构

- `Core/Text/LanguageDetection.cs`：决策层（长度 20 / CJK 放宽到 4 / 置信度差 0.1 / nb→no）
  + `AssistantLanguageProbe`（256 码点滑动窗口，判出即冻结）
- `Core/Pipeline/ResponseLanguageResolver.cs`：响应级语言四元组，**一轮只解析一次**
- `Backends.Lingua/LinguaLanguageDetector.cs`：适配器，ISO 639-3 名称 → 639-1 的 75 项映射表
  由 lingua-py 导出而非手抄；原生库缺失抛 `BackendUnavailableException`
- `tools/LanguageProbe` + `tools/refprobe/lang_probe.py`：输出 `detected` + **`windows` 数组**

### 为什么语料要比 windows 而不只比 detected

结论只有「判出/没判出」两种取值。窗口累积或截断错了，结论可能碰巧一样，
要到长回复或中途换语言才暴露。窗口是那条规则的直接投影，所以它是断言的一部分。

### 顺带发现的真实缺陷：emoji 被写成代理对转义（C017）

做语言语料时 `emoji-heavy` 那条两侧不一致，一路查下去发现不是探针问题，而是**产品序列化**：
`JavaScriptEncoder.UnsafeRelaxedJsonEscaping` 仍会转义代理码元，BMP 外的字符被写成
`\uD83D\uDE00`，而上游 `ensure_ascii=False` 原样输出。C012 只解决了 BMP 内的中文与 base64 的加号。

修法：自写 `RelaxedJsonEncoder`（只转 `"` `\` 与 0x00–0x1F，短转义优先，其余 `\u00xx` 小写），
下沉到 `Core/Json`，与 `WireJson.Compact/Indented` 一起给产品与探针共用。
**探针另配一份 options 就会让产品修好、基线还停在旧形态**——这是这次差点踩到的坑。
自定义 encoder 的抽象方法签名带 `char*`，`AllowUnsafeBlocks` 因此只开在 Core。

### 另一个顺带修的：纯文本响应白跑一次合成（C018）

上游同一处 `response_wants_audio` 判断既挡合成，也挡语言观察与解析。我们只判了「文本非空」。

### 两处「不修正」是刻意的

- 窗口拼接 `("a" + " " + " b").strip()` = `"a  b"`（两个空格）。上游如此，改了就不等价。
- `0.6 - 0.5` 在双精度下是 0.0999…98，会掉到 0.1 阈值下。上游也是这个浮点，
  所以边界用例改用二进制可精确表示的 0.75/0.5。

## 回合续：D015 Smart Turn 端点判定（拆成「判定器」与「决策层」两件事）

### 先把缺口拆开，而不是硬啃模型

原先 D015 记的是「Smart Turn 未知，宽限恒取配置值」。真正卡住的不是决策规则，而是**分类器**：
`pipecat-ai/smart-turn-v3.2` 的 ONNX 模型 + Whisper log-mel 前端。HuggingFace 当前不可达、
参照环境也没有 onnxruntime/transformers（PyPI 同样不通），所以模型这一个环节**没有任何可比对的基线**。

结论：判定器只回答「说完了没有」，宽限/延迟是纯函数。后者能完整移植并差分，前者留缺口。
于是拆成 D015（已解决：决策层 + 接合点 + 语料）与 D018（真实缺口：判定器实现）。

### 决策层的四条分支

上游 `_smart_turn_timing_ms`：

| 情形 | 宽限 | 处理延迟 | status |
|---|---|---|---|
| 没有判定器 | `speculative_reopen_ms` | 0 | `disabled` |
| 判定器抛异常 | `speculative_reopen_ms` | 0 | `failed` |
| 说完了 | `speculative_reopen_ms` | 0 | `complete` |
| 没说完 | `smart_turn_max_wait_ms` | `min(incomplete_delay_ms, max_wait_ms)` | `incomplete` |

两处容易写错：`probability > threshold` 是**严格大于**（等号算没说完，差一个等号宽限就从
2000 掉到 800）；`disabled` 时分析耗时记 **null 而非 0**（0 会在时延分解里混进假样本）。

### 接合点三处，都是「不报错但行为错」的类型

1. **判定看整轮，不是最后一段**。上游 `_speculative_raw_audio_prefix`：用户分两次说完同一句，
   第二次判定要含前半截。第一次写成每次 `SpeechStarted` 都清空，被单测抓到（第二次只拿到 3 个样本）。
   正确做法是**只在开新轮时清空**——复开是同轮 revision+1，清掉就只剩后半截。
2. **复开窗口要把 `smart_turn_max_wait_ms` 算进去**。原实现只取 `max(800, 7000)`。
   漏掉的话，判定刚说完「没说完」，窗口却已经关了，用户接着说的几个字会被判成新的一轮。
3. **配置校验要在启动路径上跑**。上游在 `__init__` 抛，那就是启动期；本实现的 handler 按连接懒建，
   只在构造期校验等于「客户端连上来才知道配错了」。手工试 `--smart_turn_max_wait_ms 0` 才发现——
   它照常 listening 了。抽出 `TurnEndOptions.Validate()`，`OptionsBuilder` 与 `VadHandler` 各调一次。

### 这一层的语料与前几层都不同

判定器是**替身**（结论由语料指定），比的是「拿到结论之后怎么办」。参照侧 `vad_handler.py`
顶层 `import torch`，环境没有 torch，于是探针往 `sys.modules` 塞了个桩模块让导入通过——
被测的两个方法（`_smart_turn_timing_ms` / `_prepare_audio`）都不碰 torch，调的是上游源码本身。

窗口那三条（左补零 / 取尾 / 精确 8 秒）按 **float32 位模式**比，不比特十进制：
浮点的最短表示是两侧运行时各自的策略。为了让失败可诊断，另带首尾样本、补零计数与整窗
FNV-1a 校验——只有一个 hash 不同的话，只看得到「不一致」三个字。

音频不进语料文件：按 `((i*37) % 1000) / 1000.0` 现场生成。只用到整数运算与一次
`double → float32` 转换，IEEE 转换确定性保证两侧逐位相同。

### 录制时踩到的坑（正是「基线必须由参照实现录」的理由）

第一版 `timing-complete` 录出来是 `incomplete`：探针把 `probability` 从 `config` 里读，
而语料把它放在 payload 顶层，于是恒取 0.0。**如果基线是手写的，这个错永远发现不了**——
手写的人会照着「0.93 应该判成说完」写下正确答案，而探针一直在用 0.0 跑。
修完探针重录，13/13 通过。

### 顺带修的：中文告警在 UTF-8 终端里是乱码（C019）

新增的启动告警必须被看见。.NET 接控制台时默认用系统代码页（936），Python 的 PEP 528
让控制台也用 UTF-8——所以同一条中文告警在 Git Bash / Windows Terminal 里是乱码。
`Program.Main` 开头把 `Console.OutputEncoding` 设为无 BOM UTF-8，拿不到控制台句柄时忽略异常
（那种情况下输出本来就是重定向的，默认已是 UTF-8）。只影响 CLI，探针各自写 stdout 不受影响。

## 回合续：D016 响应时延账与 response.metadata

### 先把占位的账本拆掉

原有一个 `TurnLatencyStore`，按 `turn_id` 存原始时间戳（语音结束/转写完成/首音频/响应结束），
再算差值。它看起来能用，但和上游是**两种结构**：上游按 `response_key` 存阶段耗时，还有一套
「待定轮次槽位 + 会话索引 + 区间并集」。同一轮里工具调用与它的口头回答是两条响应，
按轮次存会把两者的 `llm_s` 挤进同一个格子。

所以整份替换，不是扩展。三个类型按上游 420 行重写：`TurnLatencyTracker` / `TurnLatencyStore` /
`SpeechLatencyAnchor`。顺手把三处旧调用点改对——
`LmOutputProcessor.MarkFirstAudio` 记的其实是「首个文本分片」，与 `tts_ttfa` 无关（那是模型音频到达），删掉；
`LanguageModelHandler.MarkResponseDone` 改成正经的 `RecordLlm`，并且不按「有没有 turn_id」筛：
客户端独立创建的响应照样要有 `llm_s`，它只是没有 `e2e`。

### 三处「不会报错但数字会骗人」

1. **`hold_s` 是等待区间的并集**，不是各段相加。4 个 worker 同时等 0.2 秒是 0.2 秒，相加算成 0.8。
   上游合并重叠区间后求和，语料用两段重叠（10.0–10.3、10.2–10.4）锁成 0.4。
2. **`e2e_s` 一条链上只取一次**。名额由 `SpeechLatencyAnchor` 消费，用完即失效；
   工具续接链上的第二条响应共用一个名额，否则同一句话被量两次。
3. **`round(x, 9)` 只用在 `vad_decision_s` / `hold_s`**，其余字段原样写。这个不对称很容易被
   「统一保留几位小数」的直觉抹平。

### metadata 里存的是字符串，不是数字

这是本轮最容易静默漂的地方。上游：
`json.dumps(metadata_payload(...), separators=(",", ":"), sort_keys=True)`。

动手前先拿 12 个值在两侧各跑一遍格式化，确认 `.2f` 与 `F2` 连中点舍入都一致
（`0.125 → 0.12`、`0.135 → 0.14`、`2.675 → 2.67`），而**最短表示的默认写法真的不同**：
`2.0` vs `2`、`1e-07` vs `1E-07`。所以 `MetadataPayloadJson` 走 `Utf8JsonWriter` 手写 +
`RenderFloat` 两个补丁，不走产品序列化入口。

顺带删掉了同时存在的 `MetadataPayload`（JsonObject 版）。两处各写一份，浮点规则一改只会改一处。

### 合并规则单列成纯函数

`_build_response` 里与 metadata 有关的五条规则纠缠在一起，任何一条漏掉都不会抛异常，
只是客户端多看到或少看到几个键。抽成 `ResponseMetadata.Assemble`（13 条单测）：
客户端键全保留且键序不动；`s2s_tool_input_call_ids` 先删（服务端自有）；终态删掉客户端自带的
latency 键再重写；16 槽位与 512 字符两个上限都按「不删客户端键」处理；空结果发 null 不发空对象。

客户端 metadata 的解析也挪进协议层（`ReadClientMetadata`）——非字符串的值跳过而不是强转，
强转会抛，把一条本来能跑的请求变成 400。

### 顺序坑：先 build 再 pop

上游 `finish_response` 里 `terminal_response = self._build_response(...)` 在 `_end_response()`
之前，而 `_end_response` 里的 `_log_turn_latency` 才 `pop` 掉 tracker。顺序反过来的话，
终态载荷永远没有数字，而且不会报错。

日志行写 **stderr**：Python `logging` 默认 handler 就是 stderr，stdout 在 `local`/`talk` 模式下
留给语音转写，混在一起的话重定向到文件的人分不清哪行是日志。

### 新语料 corpus/latency（16 条）

操作脚本驱动（16 种 op，与上游 API 一一对应），时间全部由语料给定——没有时钟就没有抖动，
不需要容差。返回纯量 + 两个逐字符产物（压缩 JSON、日志行）。

其中 `anchor_attach_existing` 是刻意的显式操作：上游在 `bind_response_latency_tracker` 里
从 `speech_latency_anchors[(turn_id, revision)]` 查出来挂上，探针把这一步写进脚本，
免得「名额共享」这件事藏在夹具里。

## 回合续：D019 测量点接线，顺带查出更早的缺口 D021

### 先按计划做 D019，结果被 `hold_s` 挡回来了

计划是「四项测量点三步写入」。写到 `hold_s` 时发现它无处可写：`hold_s` 记的是**输出被压了多久**，
而全工程没有一处调用 `WaitForGate`——`SegmentFinalized` 算出了 `TurnGate(Hold, 800ms)`，
`ProcessingDeadline` 也算出了处理延迟，但没有任何阶段去等。也就是说上一轮 C006 移植的状态机
**结论只是建议性的**：陈旧轮次的文字照样说出口，改动一行没改也一样。

这个缺口比 metadata 字段重要，先补它。

### D021：两处阻塞，一处在输出侧，一处在输入侧

- **输出侧** `LmOutputProcessor`：每片 `LlmResponseChunk` 阻塞等闸门（`holdForGrace` 默认 true），
  陈旧就整片丢弃。上游同一位置就是这个调用。
- **输入侧** `SttHandler`：按 `ProcessingDeadline` 阻塞，但 `holdForGrace=false`。
  宽限只压输出；压住输入会让用户续说时新旧两段音频互相等，谁也不先出转写
  ——表现为「说完话要等两秒才开始识别」。已单测锁住「不该等宽限」这一条。

一个必须想清楚的点：**陈旧收尾不能直接丢**。丢了客户端永远等不到 `response.done`。
上游的处置是照发「生成结束」事件但 `succeeded=False`，让历史层拒绝这一轮。
照搬：给 `AssistantResponseDoneEvent` 加 `Succeeded`，`FinishResponseAsync` 据此回滚历史
但**不改上报状态**——对客户端它是正常收口的，只是这一轮的字没发出去、不该留在聊天记录里。

### D019：四项各自的口径

- `stt_s` 只量转写本身（不含闸门等待，否则「模型慢」和「管线堵」分不开），挂待定槽位
  ——此刻响应键通常还不存在，就地丢弃会让这一格永久 null。
- `vad_decision_s` 从**最后一个有声窗**反推，不是段尾。段尾含闭合静音，拿段尾算会得到
  「判定零延迟」这个漂亮的假象。公式抽成纯函数 `VadDecisionTiming.Decide`，四条算术单测
  （含上游那条 `max(0, ...)` 钳制与「缺锚点记 null 不记 0」）。
- `smart_status` / 宽限 / 处理延迟在定稿处**成组写**（`RecordSegmentFinalized`）。
  `disabled` 时只写 status，三项不写——写了会让时延分解里凭空多出一段不存在的判定等待。
- `hold_s` 由 `WaitObserver` 折算成区间并集。观察者挂在账本上，而不是让每个等待方各自记账。

有声窗位置怎么拿到：**不改后端接口**，加在 `VadFrame` 上。帧本来就是「后端告诉 handler 这一块
发生了什么」的载体。`SileroVadBackend` 用既有的能量门限判有声（与 D002 的开口近似同一处取舍），
粒度是一整块，与上游一个 VAD 窗同量级。

1. **VAD 在线切段用错了库的接口**（C020）。`GetResults([stream])` 是离线批处理口径，对活着的流
   不推进前向；端点判定还要 `OnlineStream.IsFinished(isEndpoint: true)` 来驱动（它内部推进静音计数
   和最长语音段上界）。两者都没做 → 真实后端一个段都不吐，管线停在 `speech_started`。
   正确顺序：`AddSamples` → `IsFinished(isEndpoint: true)` → `GetResult(stream)`。
   修后同一段音频在 6.11s 切出 95584 样本的段。
   假后端、纯函数语料都发现不了这个——三层全绿，只有真跑会死。
2. **通知器多转发了一份转写**（C021）。上游 `TranscriptionNotifier` 在 Transcription 分支只往文本队列
   发事件、不向下游返回；生成请求由 RealtimeService 发起。多出来的那份在 LM 队列里变成
   `unexpected input type Transcription`。顺带：空转写不该建用户消息、不该 `response.created`。
3. **连接建立异常没有出口**（C022）。`Map("/v1/realtime")` 裸调，后端模型路径写错时 Kestrel 静默关 socket，
   客户端只看到「连上又断开」。接住 → stderr 记一条 → 尽力发 `error` 事件。**正是它把 C020 的
   YamlException 暴露出来的**：没有这一步，真跑只会表现为「什么都没发生」。
4. 时延账在真跑里是活的：`stt=1.74s llm=5.00s vad_decision=0.07s`，`smart_turn_status=disabled`，
   `e2e/tts_ttfa` 因为没合成所以是 null。数字合理，说明测量点接线是对的。

## 第二轮会话（晚间）：真跑两轮 + 打断，C023/C024

### C023：ManySpeech OnlineVad 一条流用到底 → 第二段永远不出

- 现象：同连接第二句话 `speech_started` 有（能量门限在产品侧）、`speech_stopped` 永远不来。**先怀疑了状态机**（`_committed` 阻断复开），逐行对照上游 `speculative_turns.py` 后确认状态机一致——根因在 VAD 后端：`DecodeMulti` 只在 `Segments.Count` 增长时吐最后一段，第一段闭合后同一条 OnlineStream 再也不出段。
- 定位路径：VadProbe 合成两段语音的 wav → `--online-raw` 直连库看每块段数 → 新增 `--online-renew`（每段换流）验证两段全出 → 再改产品代码。**先在探针里证明修法有效，再动产品**，这条路这次又省了大量试错。
- 修法：每吐一个 `SpeechStopped` 就换新流；时间轴用会话累计样本数统一到连接绝对位置；段边界 `SegmentEntity.Start/End ÷ 16`。
- 教训：**「第二轮丢失」不要先入为主归因于最复杂的那层**。日志里 `陈旧轮次的收尾` 是旁证不是主因。

### C024：取消丢弃只看 Discarding 标记 → 打断后整条连接的输出全被吞

- 现象：gap 3 打断场景第二轮只有 `response.created` 和空 `response.done`，中间零分片，服务端日志一切正常。
- 上游判据是 `discarding AND generation != self._gen` 两条合取；我移植时只抄了前半。打断路径只 `Cancel` 不 `ResponseDone`，标记永久亮着。
- 修法：`CancelScope.IsDiscardable(generation)` 代际判断；三处调用点（LM 分片 / TTS 逐句 / 音频输出）全部带各自代际；`ResponseDone(generation)` 允许当前代际清标记、更早代际的迟到通知不清。
- 教训（再次验证）：**这类缺陷语料锁不住、日志查不出**——只有假后端断言「打断后新一轮的值真的到了末端」能锁。CancelScopeDiscardTests 10 例。

### 三个大坑（排查路径都值得记）

1. **FFT 分解错**：CT 内级必须**跨步 25** 取样（x[25·j1+j2]），我写成连续 16 分块——对复数 fixture 碰巧也能过部分 bin，实输入非 DC 频点全错。教训：**FFT 单测要覆盖实输入**；「部分 bin 对」不代表变换正确。
2. **do_normalize 语义**：transformers `WhisperFeatureExtractor.__call__` 的 `do_normalize=True` 是对**原始波形**做零均值单位方差（var+1e-7），不是 max-8 钳制（那个恒在 spectrogram 里做）。合成音频 std=0.19 → 功率因子差 26.7。教训：**关键字参数的真实语义要读实现，不能望文生义**。
3. **ORT 版本敏感**：同模型同特征，onnxruntime 1.27.0 概率 0.4219、1.31.0 给 0.5393（差 0.12）。定位方法：C# 特征导出 bin → Python 各版本 ORT 交叉喂入。**C# NuGet 必须钉与参照录制环境一致的版本**（已钉 1.31.0）。
