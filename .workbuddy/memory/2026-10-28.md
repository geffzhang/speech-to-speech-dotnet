## D035：talk/local 音频客户端为精简版（发现 → 收口，一条日内闭环）

### 起因

「继续下一步」巡检还没验过的部分。`talk`/`local` 客户端只有 367 行，上游 `audio_client.py` 有 1237 行。
差距不在「能不能连」，在**参数与协议面**：

- 上游参数族（talk 裸名 / local `--local-audio-*` 前缀）本实现**一个都没解析**——CommandLine 接受
  任意 `--xxx` 后无人消费。比 D034「接受却忽略」更早一步：连解析层都没有。
- `session.update` 硬编码双向 24000 并无条件声明 format；上游 16000 时 **format 整体省略**
  （`maybe_pcm_format`：16k→None，24k→显式，其余报错），客户端因此把 16k 麦克风强制上采样 24k。
- `extensions` 缺省 false 是**真功能缺失**：服务端只给订阅者发实时转写快照
  （`InputAudioTranscriptionSnapshotsEnabled`），不订阅 local/talk 下永远看不到逐字转写。
  而 `interrupt_response` 缺省 true——缺它**侥幸等价**，不是功能缺陷。查缺省值是关键一步。

### 修法（全部落地）

- `RealtimeAudioClientOptions` + `BuildSessionUpdate`（静态可测）；`FromTalkArgs`/`FromLocalArgs`
  参数装配工厂。local 的 playback_buffer_ms 缺省按 TTS 后端：openai→196 否则 0。
- `PlaybackBuffer`：首包攒满 startup_buffer_ms 才开播、`finish()` 放行短响应、欠读回 idle、
  append 后 150ms 内 `IsActive()` 恒真、clear 时机（speech_started / cancelled / cleared）。
  内部 head/tail 双游标字节数组。**NAudio 3.x `IWaveProvider.Read` 只有 Span 签名**（XML 文档里
  看到的三参 byte[] 是 2.x 的，别信缓存目录里的旧版本）。
- 麦克风按 send_rate **直通**，不再重采样。
- 设备索引贯通三后端：WinMM `DeviceNumber` / WASAPI `EnumerateAudioEndPoints`（注意大写 P，不是
  `EnumAudioEndpoints`）/ ALSA 映射 `plughw:<n>,0` / PortAudio 索引直通；越界显式报错不静默回落。
- 渲染：conversation_only / print_json / verbose 三态；snapshot 事件可见；`speech_stopped` 与
  `output_item.*` 显式不打事件名（上游 return 同款，否则 print_json 下双打印）。

### 真跑（真权重 serve 8794 + talk --print-json 12s）

麦克风环境音 → 16k 直通上行 → VAD commit（audio_end_ms=4736）→ 转写完成 → response.created →
transcript delta，零 error。新 session.update 被服务端完整接受。

### 两个环境事实（下次真跑别再踩）

1. **talk 真跑必须带全模型路径起 serve**：缺 VAD 模型目录时服务端在**连接构建期**即报
   BackendUnavailableException，session.created 都不发。客户端侧表现是「连上了但什么都收不到」，
   非常像客户端 bug——先看 serve 日志再怀疑客户端。
2. **timeout 杀 Windows 进程不彻底**：残留 talk/serve 锁住 speech-to-speech.exe → MSB3027。
   跑完确认进程清干净（`Get-Process speech-to-speech | Stop-Process -Force`）再 build。

## previous_item_id 对齐上游（2afd96a / 5e12362，用户按 B 执行）

- **背景**：SIPSorcery DTO 把 previous_item_id 声明为 C# required（非空），我们首个项省略该键 → SIPSorcery 反序列化告警 + RealtimeUnknown 降级。用户问「是不是要改 SIPSorcery 代码」→ 查证后结论：**不用改库**，真正对不齐的是我们服务端。
- **根因**：上游 Python `event.model_dump()`（transports.py:67，**不 exclude_none**）→ previous_item_id 键始终存在、首个项为 null；我们 ServerEvent 用 `if (previousItemId is not null)`，首个项省略键。
- **修复（方案 B）**：ServerEvent.InputAudioBufferCommitted / ConversationItemCreated 去掉 if 条件，**始终写键**（null 为首项）。这是此前被语料 note 锁定的「省略契约」，但该契约与上游/OpenAI 相抵触，故改。
- **影响面已核**：单测 ProtocolShapeTests（Omits→WritesPreviousItemIdNullForFirstItem）、语料 input-audio-committed-first-item note+expected。**我们自家客户端不读该字段**，不受影响。
- **验证**：协议语料 verify **--json-canonical** 43/43；全量测试 503/503；构建 0 警告 0 错误。服务端 wire 由探针确认 `previous_item_id:null`；**最小反序列化冒烟**（临时 __desercheck 工程，已删）确认 SIPSorcery 接受 null——解析为 RealtimeServerEventInputAudioBufferCommitted、PreviousItemID=null、不降级。
- **教训/要点**：① 协议语料 verify 必须带 **--json-canonical**（探针输出是紧凑+插入序，baseline 是带空格+字母序，需按 JSON 语义归一化比对；不带会全部误报）。② SIPSorcery 的 `JsonOptions` 在命名空间 `SIPSorcery.OpenAI.Realtime`（非 Models），反序列化冒烟时踩过。③ 探针验证时 `stdin_payload` 从 input.json 提取 `payload` 段喂 stdin，手动喂要传 `{"event":...}` 而非 `{"payload":...}`。
